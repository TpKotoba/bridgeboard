# 橋牌賽事記分板：可行性與任務規劃

評估日期：2026-10-11；範圍更新：2026-10-12（Asia/Taipei）

參考：https://wyniki.pzbs.pl/2026/fisu/

## 結論與範圍

可自行實作具相同核心功能、相近版面與導覽方式的系統。首版同時支援隊制賽與雙人賽，部署於 Vercel，透過结果 API 保留接入本專案線上牌桌的能力。這份文件只規劃，尚未開始實作。

「復刻」分為兩種交付：

- 結果展示：匯入既有成績，提供排名、對戰、牌局與個別成績查詢。
- 完整計分：包含賽事建立、結果輸入、計算、更正、發布與權限管理。公開網站不足以證明原系統後台流程，需自行設計。

已確認範圍：隊制賽與雙人賽都納入首版，單一主辦單位、中文介面、桌面與手機可用；結果可手動輸入或 CSV 匯入。規劃預設為隊制賽 IMP／指定 VP、雙人賽 MP／百分比；具體計分政策待真實樣本確認。首版使用手動設定或匯入的對戰／movement；自動 Swiss 配對與通用 movement 產生器後續擴充。

## 已確認的參考功能與限制

透過公開 HTML 與 main.js 確認以下介面或程式支援；不代表本次 FISU 賽事全部已啟用：

- Results、Private scores、Boards、Rounds results、Butler、Cross table 導覽。
- 階段導覽、隊伍／選手追蹤搜尋、名單查看。
- 牌型、發牌者與身價顯示的容器，HCP、雙夢家與 minimax 顯示容器。
- 牌號導覽與逐副成績表。
- 單副／session／stage 的 PBN 匯出介面。
- VP 表、即時結果定期刷新、列印及投影顯示的程式支援。
- 桌面並列區塊與手機切換面板的程式支援。

頁面標示由 Tournament Calculator 產生，雙夢家分析標示 BCalc。這些是參考網站使用的產品，不代表我們能使用其程式或後台。

本次 settings.json 與 stages.json 請求回傳 404，因此未確認賽事設定、實際資料結構、已啟用功能與完整排名。尚未完成瀏覽器畫面驗證；目前不能宣稱逐像素還原或既有數據對接已可行。下一階段先釐清資料載入位置並建立頁面／狀態清單。

## 架構與資料模型

採用 Next.js、TypeScript 與外部 PostgreSQL（Neon），單一 Vercel 應用承接公開前台與主辦 API，計分模組可独立測試。

- 公開前台：排名、輪次、對戰、牌局、個別成績。
- 主辦後台：賽事設定、名單、牌型與成績匯入、手動輸入、更正、發布。
- 計分模組：共用合約分計算，分別提供隊制賽 IMP／VP 與雙人賽 MP／百分比；避免將計分放在 UI。
- 結果服務：驗證、版本管理、衍生排名與公開查詢。
- 輸入轉接器：CSV、手動輸入，以及未來線上牌桌 result.finalized 事件。

核心實體：Event、Stage、Round、Segment、Team、Pair、Player、Lineup、Match、Room、Table、MovementAssignment、BoardSet、Board、BoardResult、Adjustment、ScoringPolicy、ResultRevision。Event 明確指定賽制及計分政策，不能用缺少 Team 欄位推斷雙人賽。

每筆結果須包含賽事／對戰／節次／房間／牌號、NS 與 EW 隊伍、合約、莊家、墩數、身價、NS 原始分、來源、狀態與版本。同牌兩房結果按隊伍方向比較，不能直接相减 NS 分數。牌號可能跨節次重複，不能當全域識別碼。

上述隊伍、對戰與房間欄位適用於隊制賽。雙人賽結果則記錄 session／round／table、NS pair、EW pair、board 與比較組別；共用合約等基本結果欄位。搭檔與實際座位分開，支援轉向和輪空。相同牌號在不同牌組或比較組別不可誤合併。

雙人賽政策需指定排名組別（NS/EW 分開或合併）、每副比較樣本、同分、未打／缺分、裁判調整及不同有效牌數的計算方式。未收到結果與輪空不是零分或 pass out。首版將未定義的特殊調整列為待裁判處理，不套用臆測規則。

VP 表、比賽牌數、四捨五入、平手排序、carry-over、罰分與 Butler 規則均須由賽事政策指定。原始結果、裁判調整與衍生排名分開保存；更正後重新計算並留下稽核紀錄。

未完賽牌型須有公開時間控制。公開 API 僅回傳可公布牌型，不能只靠前端隱藏。

## 任務階段與驗收

以下是單一熟悉全端開發者的初估工作日，非交付承諾；包含一般測試與修改，不含資料等待及現場比賽支援。

| 階段 | 任務 | 驗收 | 初估 |
|---|---|---|---|
| A 參考調查與需求固定 | 實際頁面驗證、資料路徑、頁面狀態、首版規則與資料樣本 | 功能矩陣、桌面／手機版面參考、輸入格式與計分政策 | 2–3 日 |
| B 前台原型 | 建立模擬賽事、排名、輪次、對戰、牌局、個別成績、追蹤搜尋 | 可從排名一路查到單副；手機導覽及分享連結可用 | 4–6 日 |
| C 資料與計分 | 資料庫、CSV/PBN 匯入、合約分、兩房 IMP、VP、排名 | 數據集人工核對一致；缺分與錯誤匯入可辨識 | 5–8 日 |
| D 收分與更正 | 主辦登入、結果輸入、發布、更正、重算、稽核 | 更正後各頁一致；未授權者不能寫入；重送不重複計分 | 5–8 日 |
| E 試賽與部署 | 刷新、備份還原、斷線恢復、公開牌型政策、小型比賽演練 | 完整跑完賽事；可重建排名、還原資料、限制未公開牌型 | 3–5 日 |

上表保留隊制賽基礎工作的估算：A+B 約 6–9 工作日，A+B+C 約 11–17 工作日，A–E 約 19–30 工作日。加入可重複部署與還原驗收後，隊制賽基準為 21–33 日。

2026-10-12 納入雙人賽後新增工作：

| 工作 | 初估 |
|---|---|
| Pair／movement 資料、手動設定／匯入及配置驗證 | 2–3 日 |
| MP／百分比、比較組、排名及更正重算 | 3–4 日 |
| 雙人賽排名、traveler、搭檔個別成績頁 | 1–2 日 |
| 雙人賽完整樣本核對與兩賽制回歸驗收 | 2–3 日 |

首版兩賽制合計約 29–45 工作日（約 6–9 週），為一位熟悉全端開發者的規劃估算。共用框架、部署與收分，不將兩種賽制當作兩套獨立產品計價。此估算不含自動 Swiss、通用 movement 產生器、雙人賽其他計分法、所有裁判特殊調整或硬體收分整合。

## 驗證重點與主要風險

- 計分正確：以已核對 fixtures 測試身價、加倍／再加倍、超墩／倒約、pass out、IMP 邊界與 VP 表；先固定規則版本。
- 隊伍方向：測試 open/closed room 對調、部分結果未到、跨節次同牌號。
- 更正一致性：更正一房後，對戰、逐副與總排名都重算；公開結果提供版本與更新時間。
- 實際比賽操作：匯入預覽、完整錯誤回報、重送去重、並發更正衝突與操作紀錄。
- 雙人賽驗證：同分、轉向、輪空、缺分、牌數不同與同牌跨桌比較；一筆更正可能影響同副所有搭檔，不能只重算輸入者。
- 範圍膨脹：兩賽制使用預先設定的對戰／movement，裁判特殊規則與自動排賽逐項擴充。
- 原站依赖：本系統使用自己的資料與計分；與原站同步屬於另一項尚未確認可行的整合。
- 視覺參考：可重建相近版面及互動；自訂品牌、素材與實作。是否直接使用原站資產或程式需另行確認可用授權。

## 與既有專案的關係

目前工作區已有 docs/ROADMAP.md，未看到可執行應用。這項記分板可以作為獨立、較早可驗收的模組，同時支援 ROADMAP 的團隊賽計分與公開結果功能。原 ROADMAP 未在本次修改。

第一個可執行里程碑包括兩個模擬賽事：四隊固定輪次隊制賽，以及含輪空的十五對雙人賽。共用導覽與牌型，分別展示「排名 → 對戰 → 兩房逐副比較」與「排名 → 搭檔個別成績 → 單副 traveler」。接著加入兩賽制 CSV 匯入、缺分／更正及主辦後台。

開工準備：以完整計分版、兩賽制、手動／CSV 收分與繁體中文為規劃預設；模擬資料可以先推進原型。正式計分驗收前需要各一份已核對賽事樣本與明確計分政策（隊制賽 VP、平手／罰分；雙人賽 MP、movement、排名組別及特殊調整）。第一次部署前準備 Git repository、Vercel 及 Neon 環境。

## Vercel 部署調整（2026-10-11）

記分系統的預設部署目標改為 Vercel，初期評估 Hobby + Neon Free。此節取代本文件記分板部分的单機部署假設；整體線上橋牌 ROADMAP 的牌桌服務不受影響。Hobby 是否適用需依個人、非商業使用條件確認；技術上支援 Vercel 與使用哪個付費方案是兩件事。

### 技術與任務變更

- 前端固定為 Next.js + TypeScript；公開頁與主辦後台在同一應用，短時 API 使用 Node.js Route Handlers / Vercel Functions。
- PostgreSQL 改用外部 Neon；使用適合 serverless 的 driver 或 pooled endpoint，設定連線上限，函式與 DB 選鄰近區域。資料、登入狀態、更正紀錄與版本不能僅存程序記憶體。
- 應用部署不依賴 Docker Compose；Docker 可選用於本地資料庫。交付改為 Git 部署、環境變數範例、production/preview 隔離、migration 與部署指南。Migration 在受控程序執行，不在每個 request 或每個 preview build 自動修改正式 DB。
- 公開資料回傳 version、updatedAt、provisional/confirmed；前台預設 30 秒輪詢一個合併狀態 endpoint，詳細牌局按需讀取。背景分頁暂停輪詢；賽事結束後停止自動更新，錯誤時退避重試。
- 公開讀取採明確的 CDN cache policy，不依賴框架預設。為每個 URL 的 query 組合設計 cache key，設定有限 stale window，例如最多約 30–60 秒；回應顯示結果版本及更新時間。登入、寫入與未公開牌型回應禁止共用公開快取。驗證部署後的 cache HIT/MISS，不能只以本地行為判斷。
- 寫入以 DB transaction 保存原始结果、修訂紀錄及該賽事衍生快照版本，完成後再回成功。小型賽事按受影響范围同步重算；若壓測顯示過慢，再新增可靠持久化工作隊列。避免依賴 response 後無保證的背景工作。
- 收分增加 idempotency key、資料唯一鍵與樂觀版本檢查；保護多個 serverless instance 同時寫入或客戶端重送。
- CSV/PBN 小檔在單次短請求內匯入，設定大小／列數限制。大型檔改外部物件儲存及分批處理；上傳檔及備份不能寫到部署目錄或將 /tmp 當持久儲存。
- 排名重算由收分與更正觸發，不由排程或觀眾刷新觸發。首版不設 WebSocket server；真正牌桌即時連線後續由獨立服務承接。
- 備份採資料庫供應商能力加獨立匯出／還原流程；每日排程或外部排程工具僅用於維護，不能支撐每分鐘比分刷新。免費 DB 還原保留窗口短，試賽須驗證可用的獨立備份與故障恢復。

### 新的部署驗收

1. Preview 與正式環境 DB／登入設定隔離，公開 API 無秘密資料。
2. 不依賴本地檔案或單一 instance；重啟／擴增 instance 不遺失成績。
3. 同時收分、更正與重送不會產生重複或遺漏；每頁可核對版本，公開快取在約定時間內更新。
4. 區分 CDN requests、function invocations、DB queries、CPU、記憶體及流量，從實際監控驗證額度，不以單一 request 數保證可用性。
5. 使用 30 人／3.5 小時雙人賽、40 人／8 小時隊制賽作容量情境。單一 endpoint 每 30 秒輪詢分別約 12,600 與 38,400 次；導航、寫入、首次載入另計。依比例模擬持續負載與集中收分。
6. 測試 DB 冷啟動／額度耗盡／寫入失敗，前台保留已讀結果並清楚標示更新失敗，不能把失敗呈現成零分。
7. 備份還原與應用回退各自驗證：回退部署不會自動回退資料庫；schema 修改採相容的漸進遷移。

雙人賽已於 2026-10-12 納入首版功能與驗收。十五對、十三輪、每輪兩副的案例需依實際 movement 核對每對有效牌數；不能假設輪空者仍有二十六副有效結果。隊制賽另以四十人、八輪、每輪七副作完整演練。

### 工期與預算影響

目前只有規劃文件，無既有伺服器需要遷移。基本 Vercel 部署取代 VPS 部署；兩賽制首版估算更新為 29–45 工作日，階段 E 採上述 serverless 驗收，完成原型和壓測後再修正。

Hobby + Neon Free 在符合條件及額度內可為 USD 0/月；自訂網域、額外備份／儲存或付費 DB 另計。降低的是主機服務費，計分測試與主辦功能的開發工作仍保留。
